# V0.5 Evidence Re-resolution Hardening 实现记录

## 1. 边界

V0.5 只解决 V0.3 `knowledge_relation_evidence` 在 ExerciseUnit 或 KnowledgePoint 映射变化后的可审计重解析。

```text
immutable raw Evidence
  -> current resolution recomputation
  -> explicit editable Draft reconciliation
  -> validate
  -> separately requested publish/projection
```

重解析不会自动发布，不会写 `GRAPH_REBUILD_REQUEST`，不会修改 Course 的 active graph 指针，也不会修改 Neo4j Published Graph。没有引入 MODEL-1 数据变更、生产模型推理、LLM、Agent、Kafka 或微服务。

## 2. V005 Schema

`V005__evidence_reresolution_history_and_draft_reconciliation.sql` 新增：

- `knowledge_relation_evidence_resolution_history`
  - `evidence_id` 和 `graph_version_id`：Evidence 与受影响 Draft 的上下文；
  - old/new resolution status、ExerciseUnit endpoints、KnowledgePoint endpoints、conflict/detail：完整 before/after；
  - `operator_id`、`trigger_type`、`created_at`：操作者、触发原因和时间；
  - `before_relation_ids_json`、`after_relation_ids_json`、`reconciliation_json`：Draft evidence-link 与关系计数的审计结果。

V001–V004 未修改。`KnowledgeRelationEvidence` 的 raw course/source/external IDs/raw payload 在 JPA 映射中均为 insert-only；V0.5 只更新 derived resolution projection。

## 3. 转换与 Draft 协调规则

- 支持 `UNMAPPED_* → RESOLVED`、`AMBIGUOUS_* → RESOLVED`、`RESOLVED A→B → A→C`、`RESOLVED → unresolved/ambiguous`、`REJECTED_SELF_LOOP ↔ RESOLVED`。
- 解析使用相同的唯一 Exercise external ID 与唯一 ExerciseUnit→KnowledgePoint 映射规则；不猜测合并。
- Apply 只允许 `DRAFT` 或 `VALIDATION_FAILED` 的可重新校验 Draft 上下文；它不额外改写 GraphVersion 状态。`PUBLISHED`、`ARCHIVED`、`READY`、`PUBLISHING`、`PROJECTION_FAILED` 被明确拒绝。
- 当 pair 变化或新状态不可解析时，只从目标 Draft detach stale Evidence link，重新计算旧 relation 的实际 link 数；Evidence 来源 relation 变为零证据时标记 `REJECTED`，不再伪装为有效 candidate。
- 新 pair 在目标 Draft 中创建或聚合一个 candidate；同一 Evidence 在目标 Draft 的同一 relation 不会重复 attach。重复 Apply 在 resolution 与 Draft links 都已收敛时不会再写 history。
- PUBLISHED/ARCHIVED relation、它们的 evidence links、当前 Course active version 和当前 Neo4j 投影均不参与任何更新。

## 4. API

管理员角色（`SYSTEM_ADMIN` 或 `TEACHER`）：

- `POST /api/v1/admin/graph-versions/{graphVersionId}/evidence-reresolutions/dry-run`
- `POST /api/v1/admin/graph-versions/{graphVersionId}/evidence-reresolutions/apply`
- `GET /api/v1/admin/evidence/{evidenceId}/resolution-history`

请求体：

```json
{
  "evidenceIds": [12, 13],
  "triggerType": "MAPPING_CHANGE"
}
```

`triggerType` 可取 `ADMIN_REQUEST`、`MAPPING_CHANGE`、`CONFLICT_REVIEW`。Dry-run 返回 raw Evidence、current/proposed resolution、conflict 与 Draft impacts，但不创建或更新任何持久化记录。Apply 返回相同结构并为每个真实 resolution/Draft 变更写入 history。

现有 `GET /api/v1/admin/evidence?courseId=...` 继续返回 immutable raw payload 和 current resolution；前端可从 Evidence 条目进入重解析和 history。

## 5. 管理端

V0.3 图治理页新增 V0.5 区域：

- 查看 raw source type、external IDs、raw payload 与 current resolution/conflict；
- 选择一个目标 Draft 和一个或多个 Evidence；
- 展示 Dry-run 的 current/proposed resolution、冲突以及 candidate/link/evidence-count 影响；
- Apply 仅协调该 Draft；
- 展示 history 中的 Draft、before/after、operator、trigger 与时间。

## 6. 验证覆盖

真实 MySQL 8.4 Testcontainers 覆盖：

- `UNMAPPED → RESOLVED` 和 immutable raw payload；
- `AMBIGUOUS → RESOLVED`；
- `A→B → A→C`、stale link detach 和聚合 evidence_count；
- `RESOLVED → AMBIGUOUS`；
- `REJECTED_SELF_LOOP → RESOLVED → REJECTED_SELF_LOOP`；
- dry-run 零持久化副作用；
- repeated Apply 的 history/link 幂等性。

真实 MySQL 8.4 + Neo4j 5.26 Testcontainers 回归：先实际发布 Evidence 支持的 V1，再复制 V2 Draft 并重解析；断言 V1 relation/link、Course active pointer、`GraphQueryService` 与 V1 Neo4j edge 不变，V2 才出现 A→C candidate。对 PUBLISHED V1 的重解析请求被拒绝。

本地最终 backend 回归命令 `mvn --batch-mode test` 通过 60 项测试（0 failure、0 error、0 skipped）。前端 `pnpm run build` 通过，data-pipeline 回归 12 项通过，`docker compose config --quiet` 通过。

## 7. Bad Cases

- Evidence 不属于目标 Draft 的 Course：拒绝，事务不产生部分 Apply；
- 请求中重复 Evidence ID：拒绝；
- unresolved/ambiguous/self-loop：保留 raw Evidence，移除目标 Draft 的 stale support，不生成可发布边；
- target Draft 之外的历史 relation/link：不触碰；
- Dry-run：不创建 import run、conflict、history、relation 或 evidence link；
- Neo4j 不可用或新 Draft 尚未发布：不相关，因为重解析不访问 Neo4j；线上继续按当前 active Published Graph 查询。

# V0.6 Teacher Course Authorization and Learning Analytics 实现记录

## 1. 交付边界

V0.6 先收紧既有课程级授权，再在该边界内提供教师学情查询。

```text
SYSTEM_ADMIN / TEACH_ADMIN
  -> Course 生命周期与教师分配
  -> 全课程教学内容、图治理与学情访问

TEACHER + ACTIVE course_teacher_assignment + ACTIVE Course
  -> 该课程教学内容、图治理与学情访问

STUDENT + ACTIVE course_enrollment + ACTIVE Course
  -> 自己的学习读写路径
```

本阶段没有接入模型生产推理、LLM、Agent、Kafka、流处理、微服务、OLAP、数据仓库或自动预警。

## 2. V006 Schema

唯一新增 migration 为 `V006__teacher_course_assignment_and_analytics_indexes.sql`；V001–V005 未改动。

- `course_teacher_assignment` 保存 `teacher_id`、`course_id`、`assignment_role`（`OWNER` / `INSTRUCTOR`）、`status`（`ACTIVE` / `INACTIVE`）、`assigned_by`、`assigned_at` 与审计时间；
- `(teacher_id, course_id)` 唯一，三个外键分别指向教师用户、课程和可空的分配操作者；
- 建立 `(course_id, status)` 与 `(teacher_id, status)` 索引；
- 为教师分析增加 `answer_record(course_id, answered_at, id)` 与 `answer_record(course_id, question_id, answered_at)` 索引。

分配服务在应用层验证目标用户处于 ACTIVE 状态且具有 `TEACHER`、`TEACH_ADMIN` 或 `SYSTEM_ADMIN` 教学角色。数据库外键不被当作角色校验的替代品。

## 3. 授权收敛

`CourseAccessService` 成为课程读与教学操作的统一检查点：

| 主体 | 课程与教学内容 | Course 生命周期与教师分配 | 教师分析 |
| --- | --- | --- | --- |
| SYSTEM_ADMIN | 全课程 | 允许 | 全课程 |
| TEACH_ADMIN | 全课程 | 允许 | 全课程 |
| TEACHER | 仅 ACTIVE assignment 对应的 ACTIVE Course | 拒绝 | 仅该课程 |
| STUDENT | 仅 ACTIVE enrollment 对应的 ACTIVE Course | 拒绝 | 拒绝 |

普通教师不再拥有全课程旁路；课程禁用或 assignment 停用后都会被拒绝。

所有容易被猜测的间接资源都会先还原课程再授权：

- KnowledgeArea / KnowledgePoint 还原 `courseId`；
- ExerciseUnit、Question 与 ExerciseUnit–KnowledgePoint mapping 还原所属课程，更新时同时检查原课程和目标课程；
- GraphVersion、relation、validation issue 还原 GraphVersion 的 `courseId`；
- Evidence、Evidence resolution history、import run conflict 还原 Evidence 或 import run 的 `courseId`；
- Student detail 先检查教师的课程权限，再检查目标学生是该课程 ACTIVE enrollment。

Course lifecycle 和 assignment controller 只接受 `SYSTEM_ADMIN` / `TEACH_ADMIN`。既有 Knowledge、Exercise、Question、Graph、Evidence 管理 controller 则允许教学角色进入控制器，但每个服务调用都执行上表的课程级检查。

## 4. API

教师 assignment 管理：

- `GET /api/v1/admin/courses/{courseId}/teachers`
- `POST /api/v1/admin/courses/{courseId}/teachers`
- `PUT /api/v1/admin/courses/{courseId}/teachers/{teacherId}`
- `DELETE /api/v1/admin/courses/{courseId}/teachers/{teacherId}`

教师分析：

- `GET /api/v1/teacher/courses`
- `GET /api/v1/teacher/courses/{courseId}/analytics/overview`
- `GET /api/v1/teacher/courses/{courseId}/analytics/knowledge-points`
- `GET /api/v1/teacher/courses/{courseId}/analytics/mastery-heatmap?page=&size=`
- `GET /api/v1/teacher/courses/{courseId}/analytics/questions/errors`
- `GET /api/v1/teacher/courses/{courseId}/students/{studentId}/analytics`

`from` 与 `to` 必须同时提供或同时省略；默认窗口为最近 30 天，最大窗口为 365 天，响应会返回实际解析后的窗口。MySQL `DATETIME` 绑定和读取按 UTC 显式转换，避免主机时区使窗口统计漏数。

## 5. 数据与统计语义

教师分析只查询 Platform Business Domain：课程、ACTIVE enrollment、`answer_record`、KnowledgePoint、当前 mastery / history、recommendation snapshot / item 和课程的 Published Graph metadata。Junyi Research Student 与 ProblemLog 没有进入教师端学生列表或任何统计分母。

- overview、KnowledgePoint 作答量和高错题使用请求窗口内的 ACTIVE enrolled student 作答；分母为零时 rate 为 `null`；
- KnowledgePoint mastery 是当前状态，响应明确该语义；`UNKNOWN` 的 mastery score 为 `null`，单独计数且不参与平均值和弱项计数；
- heatmap 按学生分页（默认 50，最大 100），一次取页面学生、ACTIVE KnowledgePoint 与对应 mastery，不为每个学生或知识点循环查询；
- 高错题默认要求至少 5 次作答，排序为 wrong rate 降序、wrong count 降序、questionId 升序；
- Student detail 返回当前 mastery、弱项、最近作答、mastery history 与最新 recommendation context，不返回学生提交答案内容。

## 6. 前端

Vue 前端新增“教师工作台”：

- 已授权教师课程选择和受控时间窗口；
- course overview、KnowledgePoint OBSERVED / UNKNOWN 统计；
- 分页 Student × KnowledgePoint heatmap；
- high-error Question；
- 可下钻的学生详情、近期作答、mastery history、最新 recommendation context；
- 明确提示数据只来自 Platform Business Domain。

管理页将 Course 生命周期和教师分配限制为平台教学管理员；普通教师仍可在已分配课程内管理目录、题库与 Graph / Evidence，前端不再把 Course lifecycle 操作呈现为普通教师能力。

## 7. MySQL 8.4 验证

`TeacherAuthorizationMySqlIntegrationTest` 使用真实 `mysql:8.4` Testcontainers fixture：

```text
Teacher-A -> Course-A ACTIVE assignment
Teacher-B -> Course-B ACTIVE assignment
Student-A -> Course-A ACTIVE enrollment
Student-B -> Course-B ACTIVE enrollment
```

它验证 Teacher-A 可以访问 Course-A 教学数据，但对猜测的 Course-B、Student-B、Knowledge、Exercise、Question、GraphVersion、Evidence history、Evidence import run、Course lifecycle 与 teacher assignment 路径均得到 403；Student-A 猜测 Course-B Question 也得到 403。TEACH_ADMIN / SYSTEM_ADMIN 被允许，停用 assignment 被拒绝，停用 enrollment 不计入 heatmap。

`TeacherAnalyticsMySqlIntegrationTest` 使用平台用户、课程、选课、真实答题、规则 mastery 与 recommendation fixture，验证 overview、正确率、OBSERVED / UNKNOWN、heatmap、高错题稳定排序、student detail、recent answers、mastery history、recommendation context、空窗口 `null` rate，以及跨课程拒绝。

## 8. 受控性能记录

这不是 HTTP 压测或生产性能承诺。它是直接 service 调用真实 MySQL 8.4 Testcontainer 的受控本地测量：3 次预热、21 次采样，fixture 为 31 名 ACTIVE Platform student、2 个 ACTIVE KnowledgePoint、310 条 AnswerRecord。

环境：Windows 11 64 位（10.0.26200）、Intel Core i5-10200H（4 核 / 8 逻辑处理器）、15.91 GiB 物理内存、Docker Desktop Engine 29.6.2（容器可用内存 7893 MB）、Java 21.0.12、Testcontainers 2.0.5、`mysql:8.4`。

| --- | ---: | ---: |
| course overview | 13 ms | 16 ms |
| KnowledgePoint analytics | 11 ms | 13 ms |
| heatmap page（size 25） | 12 ms | 17 ms |
| high-error questions | 12 ms | 16 ms |

这些结果满足本阶段的工程参考目标，但不外推为真实生产容量结论。

## 10. Bad Cases 与限制

- 只传 `from` 或 `to`、结束时间不晚于开始时间、窗口超过 365 天、负页码、heatmap size 超过 100、明细 limit 不在边界内均被拒绝；
- `UNKNOWN` 不显示为数值 mastery，也不进入平均值或弱项；
- 未达到 minimum attempts 的题目不会因单次错误而出现在高错题榜首；
- 不是目标课程 ACTIVE enrollment 的学生不能被教师下钻；
- ACTIVE assignment 不会绕过 DISABLED Course；
- 本阶段没有第二套 analytics 真相或预聚合基础设施。出现真实瓶颈前，不以缓存或新基础设施掩盖查询问题。

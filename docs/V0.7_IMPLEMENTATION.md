# V0.7 Release Readiness — Implementation Record

## Scope

V0.7 converts the V0.6 modular monolith into a reproducible local/reviewer Release Candidate. It does not add an education business feature or integrate MODEL-3, LLM/Agent, Kafka, Kubernetes, microservices, cloud-vendor services, or a production SLA.

## Delivered implementation

- `docker-compose.full.yml` starts real MySQL 8.4, Redis 7.4, Neo4j 5.26, backend, and production frontend. The backend image compiles itself in a Docker multi-stage build; the frontend image builds Vue in Node and serves it through Nginx.
- Clean volumes run Flyway `V001`–`V006`. The optional synthetic Platform Demo seed runs after migration and creates a small valid Published DAG through the normal validate/publish/worker path.
- `.env.example`, release-mode validation, environment generation helpers, external CORS/API/issuer settings, and `.gitignore` prevent the release path from selecting placeholder or development credentials silently.
- Actuator liveness/readiness, version/info, public OpenAPI YAML, request correlation header/logging, and sanitized data-integrity errors are provided. MySQL/Neo4j are critical readiness dependencies; Redis is a documented optional-cache `DEGRADED` state.
- The `DEMO-*` fixture separates Platform Business Domain users from Junyi research identity/data. It supplies the required administrator, two teachers, four students, two courses, assignments, enrollments, questions, graph, controlled answer, RuleBeta mastery, recommendation snapshot, and path target.
- The system-admin-only recovery action reprojects active Published graph snapshots from MySQL into Neo4j without mutating GraphVersion lifecycle state.
- Containerized Node smoke and Playwright browser E2E cover student, teacher, Course-A/Course-B 403, admin assignment/governance visibility, real graph query, readiness, OpenAPI, and JWT failure envelopes. Reports are machine-readable and retained as CI artifacts.
- Backup/restore and validation scripts plus deployment/runbook/demo/architecture documentation are included.
- GitHub Actions retains backend, Python, frontend and base compose checks and adds the `full-stack-release` gate.

## Verification record

### Local full-stack evidence — 2026-09-08

The following was executed against a clean local Compose project on an Intel i5-10200H host (8 logical processors, 15.9 GiB RAM), with a synthetic 2-course / 7-user Platform Demo fixture. These are local evidence points, not a production-capacity claim.

- Clean volumes reached readiness in **68.7 seconds**. MySQL reported exactly six successful Flyway rows: `001,002,003,004,005,006`.
- The native real-HTTP smoke passed after the clean start. It exercised liveness/readiness/version/OpenAPI, synthetic student answer → mastery → recommendation → learning path, Published Graph query, teacher analytics, Teacher A → Course B `403`, administrator assignment lookup, Published Graph reprojection, missing-JWT `401`, and authenticated missing-route `404`.
- An independent real-browser run completed the student UI flow (login, course, answer, mastery, recommendation, learning path), teacher workspace (assigned course, overview, KnowledgePoint analytics, heatmap, student detail), and administrator assignment / Published Graph governance views. This is equivalent browser evidence; the container Playwright run remains the authoritative CI browser gate.
- MySQL authority and Neo4j projection were queried directly: one Published GraphVersion / one approved Published relation in MySQL, then two projected KnowledgePoint nodes / one `PREREQUISITE` edge in Neo4j. Neo4j restart followed by administrator reprojection passed.
- Backend restart followed by smoke passed; frontend restart retained SPA deep-link HTTP 200. MySQL stop produced readiness HTTP 503 / `DOWN`; Redis stop produced HTTP 200 / `DEGRADED`; both recovered to `UP` and passed smoke.
- MySQL backup → clean volumes → restore returned the same validation counts (six Flyway rows, seven users, two active courses, AnswerRecord, mastery, one Published GraphVersion, one approved Published relation). Starting from an empty Neo4j volume, the MySQL Published relation reprojection restored the two-node / one-edge graph.
- Indicative ten-sample local latency results were recorded in ignored `artifacts/performance-v07.json`: answer p50/p95 **44.3/71.7 ms**, mastery read **35.6/54.8 ms**, recommendation **120.1/155.0 ms**, learning path **120.8/201.2 ms**, teacher overview **38.7/117.9 ms**, KnowledgePoint analytics **31.3/68.0 ms**, heatmap **27.4/33.2 ms**, student detail **40.1/59.7 ms**; ten concurrent mastery reads completed in **97.6 ms** wall-clock. Container snapshot at measurement time: backend 522.7 MiB, MySQL 461.9 MiB, Neo4j 731.7 MiB, Redis 11.2 MiB, frontend 8.6 MiB. These are a controlled local fixture measurement, not an SLA.

The local host lacked standalone npm and pytest packages, so frontend validation was performed by its production Docker build and Python source syntax was parsed for 44 files. Existing backend tests, containerized full-stack smoke, and the GitHub Actions Python/frontend/Playwright jobs remain required before the final gate is set.

## Known operational limits

- This is a controlled local/reviewer Compose deployment, not a high-availability or production-capacity claim.
- Neo4j is intentionally rebuildable from MySQL Published relation data; it is not an independent source of business truth.
- Redis has optional-cache semantics. An outage is visible as `DEGRADED`; it is not silently treated as success.
- Browser acceptance uses a fixed small synthetic fixture. It is not a performance benchmark against real students or Junyi data.

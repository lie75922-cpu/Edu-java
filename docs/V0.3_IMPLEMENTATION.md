# V0.3 知识关系治理与版本化 Published Graph 实现记录

## 1. 交付边界

本交付把 V0.2 的 `Course → KnowledgePoint → ExerciseUnit → Question → Answer` 扩展为以下受控闭环：

```text
raw prerequisite Evidence
  → ExerciseUnit 唯一身份解析
  → ExerciseUnit → KnowledgePoint 映射解析
  → Draft candidate relation / Evidence links
  → 人工审核或人工关系
  → GraphValidator
  → READY
  → GRAPH_REBUILD_REQUEST Outbox
  → versioned Neo4j projection + verification
  → active GraphVersion switch
  → graph queries
```

MySQL 保持关系事实、Evidence、审核状态和版本生命周期的唯一权威；Neo4j 只保存成功发布版本的可重建投影。正式业务图仅有：

```text
(:KnowledgePoint)-[:PREREQUISITE]->(:KnowledgePoint)
```

没有把 raw Junyi Exercise edge 直接写入 Neo4j，也没有导入研究 Student 或行为数据。本轮未执行真实 Junyi 数据集导入；Evidence importer 通过受控测试 fixture 验证其解析与冲突路径。

## 2. V003 Schema

`backend/src/main/resources/db/migration/V003__knowledge_relation_governance_and_versioned_graph.sql` 新增：

- `course.active_graph_version_id`：当前已发布图版本的指针；worker 仅在投影和计数验证成功后更新它。
- `graph_version`：`course_id + version_no` 唯一，记录 `DRAFT`、`VALIDATING`、`READY`、`PUBLISHING`、`PUBLISHED`、`ARCHIVED`、`VALIDATION_FAILED`、`PROJECTION_FAILED` 以及审计时间和失败原因。
- `knowledge_relation_evidence`：保存 raw payload、外部 Evidence ID、Exercise/KP 解析结果、解析状态和冲突原因；不能解析的 Evidence 仍保留。
- `knowledge_relation`：每个 GraphVersion 的 `PREREQUISITE` 快照，版本内 `(graph_version_id, source_knowledge_point_id, target_knowledge_point_id, relation_type)` 唯一。
- `knowledge_relation_evidence_link`：关系到全部 Evidence 的可追溯链接，避免只留下不可审计的聚合计数。
- `graph_validation_issue`、`knowledge_relation_evidence_import_run`、`knowledge_relation_evidence_conflict`：分别保存结构化验证问题、dry-run/apply 审计与导入冲突。

`course.active_graph_version_id` 通过发布 worker 从本 Course 的 `PUBLISHING` 版本切换；查询层再次验证指针所指版本属于同一 Course 且为 `PUBLISHED`。

## 3. Evidence 与 Draft 治理

Junyi raw prerequisite 的 API 只接收 Evidence：

1. 以 `JUNYI_CATALOG`、`external_id` 和 `identity_status=RESOLVED` 查找 source/target ExerciseUnit；多个匹配不会猜测合并。
2. 两端各自必须有且只有一条 ExerciseUnit → KnowledgePoint 映射，且两个 KnowledgePoint 属于当前 Course。
3. 成功解析后在 Draft 生成或聚合一个 `CANDIDATE` 的 `PREREQUISITE`；每条 Evidence 都保留独立 link。
4. self-loop 仍保存 Evidence，状态为 `REJECTED_SELF_LOOP`，但不形成关系。
5. 缺失、重复、未映射、歧义身份或歧义映射进入 `knowledge_relation_evidence_conflict`，不会静默变成正式边。

管理员可在 Draft 手工新增 `MANUAL` 关系、审核 candidate 为 `APPROVED` 或 `REJECTED`、逻辑拒绝 Draft 关系、查看每条关系的 Evidence。已发布版本不能直接编辑。

## 4. 验证与发布语义

`GraphValidator` 是独立领域服务，输出持久化的 `ERROR` / `WARNING` 问题：

- 错误：`SELF_LOOP`、`DUPLICATE_EDGE`、`CROSS_COURSE_EDGE`、`MISSING_SOURCE_NODE`、`MISSING_TARGET_NODE`、`INACTIVE_NODE`、`CYCLE`。
- 警告：`NO_EVIDENCE_WARNING`、`NO_EXERCISE_COVERAGE_WARNING`。

Cycle 问题保存实际代表性有向环的节点 ID、code、name 和完整环路径。任何错误使版本转为 `VALIDATION_FAILED`，不会写发布 Outbox；警告可以进入 `READY`。

发布请求仅接受 `READY`：在同一 MySQL 事务中标记 `PUBLISHING` 并写入 `GRAPH_REBUILD_REQUEST`。调度 worker 严格按该事件类型取件，完全不查询或消费 `MASTERY_UPDATE_REQUEST`。

worker 成功顺序为：创建 Neo4j 约束、投影、校验节点/边数量、切换 Course active 指针、标记新版本 `PUBLISHED`、归档旧版本、标记 Outbox 完成。投影或校验失败时新版本转为 `PROJECTION_FAILED`，Outbox 标记失败；旧图没有删除，旧 active 指针不变。

## 5. Neo4j 投影与查询

Neo4j 节点使用 `projectionKey = courseId:graphVersionId:businessId`，并建立 `KnowledgePoint.projectionKey` 唯一约束。节点还带有 `businessId`、`courseId`、`graphVersionId`、`code`、`name`；边带 `relationId`、`graphVersionId`、`relationSource`。Java 业务查询只用业务 ID，绝不读取 Neo4j 内部 node id。

每个 GraphVersion 具有独立节点和边投影。新版本投影成功前，查询继续经由 Course 的旧 active 版本；成功后才会暴露新版本。

学生/教师查询 API：

- `GET /api/v1/courses/{courseId}/graph`
- `GET /api/v1/knowledge-points/{knowledgePointId}/prerequisites`
- `GET /api/v1/knowledge-points/{knowledgePointId}/successors`
- `GET /api/v1/courses/{courseId}/graph/path?from={id}&to={id}`
- `GET /api/v1/knowledge-points/{knowledgePointId}/prerequisite-subgraph`

所有成功查询都含 `graphVersionId`。没有 Published Graph 时返回明确的业务冲突，不把空图伪装成有效图。

管理员 API：

- `POST|GET /api/v1/admin/graph-versions`、`GET /api/v1/admin/graph-versions/{id}`
- `GET|POST /api/v1/admin/graph-versions/{id}/relations`
- `PUT|DELETE /api/v1/admin/graph-versions/{id}/relations/{relationId}`
- `GET /api/v1/admin/graph-versions/{id}/relations/{relationId}/evidence`
- `POST /api/v1/admin/graph-versions/{id}/evidence-imports/dry-run`
- `POST /api/v1/admin/graph-versions/{id}/evidence-imports/apply`
- `POST /api/v1/admin/graph-versions/{id}/validate`
- `GET /api/v1/admin/graph-versions/{id}/validation-issues`
- `POST /api/v1/admin/graph-versions/{id}/publish`
- `POST /api/v1/admin/graph-versions/{id}/retry-projection`
- `GET /api/v1/admin/evidence`、`GET /api/v1/admin/evidence-imports/{importRunId}/conflicts`

## 6. 前端最小路径

学生页展示当前图版本、完整知识图、按名称或 code 搜索、选择节点后查看前驱/后继，以及两节点有向路径。管理页展示每个版本及 active 标记、关系及审核状态、Evidence、导入冲突、验证问题、发布状态和失败原因，并提供创建、复制、审核、导入、验证、发布与失败重试操作。

Vite 生产构建采用稳定的输出文件名，避免构建产物名称依赖内容指纹。

真实 Neo4j 集成用例验证了唯一约束、三节点 DAG 投影、前驱、后继、路径、子图和 V1/V2 版本隔离。恢复用例先把 V1 实际投影到 Neo4j，再在测试容器中加入一个与 V2 独立投影冲突的测试唯一约束，使 V2 的真实 Cypher 写入被 Neo4j 拒绝；断言 V2 为 `PROJECTION_FAILED`，V1 仍为 `PUBLISHED`、Course active 指针仍指向 V1，且 V1 查询继续返回原有边。

## 8. Bad Cases 与限制

- 2 节点环、3 节点环和 self-loop 都产生阻断性问题，环路响应包含实际节点序列。
- 同一 Draft 的重复关系受到数据库唯一约束和 validator 双重保护。
- 跨 Course、缺失节点、inactive 节点不会通过验证。
- source/target Exercise external ID 不存在、重复、未映射或映射歧义均只保留 Evidence/Conflict，不形成 candidate。
- 同一 KnowledgePoint pair 的多条有效 Evidence 聚合为一个 candidate，但全部 evidence link 保留。
- 新图失败不会删除旧 Neo4j 投影，也不会提前切换 active 指针。

明确不在本轮范围内：Mastery、认知诊断模型集成、推荐、个性化学习路径、LLM、Agent、Kafka、微服务拆分。V0.3 到此停止，不授予下一阶段的自动实施权限。

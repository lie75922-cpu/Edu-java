# V0.4 Scope & Acceptance — Rule Mastery, Recommendation and Learning Path

## 1. 阶段目标

V0.4 在不依赖 MODEL-0R 最终模型选择的前提下，完成平台第一个可运行的个性化学习闭环：

```text
Question Answer
  -> AnswerRecord
  -> MASTERY_UPDATE_REQUEST
  -> RuleBasedMasteryProvider
  -> Student Knowledge Mastery
  -> Published Knowledge Graph
  -> Recommendation
  -> Learning Path
  -> Structured Explanation
```

V0.4 的规则掌握度是正式工程兜底，不冒充机器学习认知诊断。

## 2. 前置基线

必须从包含 V0.3 的最新 `main` 开发，并遵守：

- ADR-0002：Area / KnowledgePoint / ExerciseUnit / Question 分层；
- ADR-0003、ADR-0005：MySQL权威 + Published Graph；
- ADR-0006：MasteryProvider + Rule fallback。

Issue #13 的 Evidence re-resolution 是独立硬化任务，不阻塞本阶段。

## 4. WP-V04.2 — Mastery Outbox Worker

实现独立 worker，只消费：

`MASTERY_UPDATE_REQUEST`

严禁消费 `GRAPH_REBUILD_REQUEST`。

流程：

```text
claim PENDING mastery event
 -> load AnswerRecord
 -> idempotency check(answerRecordId)
 -> load ExerciseUnit->KnowledgePoint mappings
 -> for each valid mapping update Rule Mastery
 -> write history
 -> mark processed answer
 -> mark outbox DONE
```

失败：
- 不存在 AnswerRecord；
- ExerciseUnit无KnowledgePoint映射；
- KnowledgePoint inactive/cross-course；
- DB异常；

必须记录明确失败原因并按现有 Outbox retry 语义处理。

同一 answer event 重放100次也只能增加一次 attempt_count。

## 5. WP-V04.3 — RuleBasedMasteryProvider

固定算法：

`RULE_BETA_1_1_V1`

```text
mastery = (correct_count + 1) / (attempt_count + 2)
```

要求：
- 第1次做对 => 2/3；
- 第1次做错 => 1/3；
- 统计值来自实际 AnswerRecord；
- 多Knowledge映射时每个KP独立更新；
- 无历史时返回 `UNKNOWN`，不要伪造0.5为“已诊断掌握度”；如果内部排序需要先验，可单独标记 prior，不在UI冒充观测 mastery。

API至少：
- `GET /api/v1/courses/{courseId}/mastery`
- `GET /api/v1/knowledge-points/{id}/mastery`
- `GET /api/v1/courses/{courseId}/mastery/history`

只允许学生看自己；教师/管理员的他人查询权限若实现，必须有course范围控制，不能沿用“任何TEACHER看所有课程”的宽松权限。

## 6. WP-V04.4 — Recommendation Engine

结构必须分层：

```text
RecommendationCandidateGenerator
RecommendationFilter
RecommendationRanker
RecommendationExplanationBuilder
```

不要把全部逻辑写进一个Service。

### Candidate
至少来源：
- mastery < 0.70 的已观测知识点；
- 这些知识点在当前 Published Graph 中尚未掌握的 prerequisite；
- ACTIVE 且存在 ACTIVE Question 的 ExerciseUnit。

### Filter
至少排除：
- inactive knowledge/exercise/question；
- 不属于课程；
- 无可练习Question的ExerciseUnit；
- 图版本与course active版本不一致的图推理结果。

### Rank
V0.4使用确定性规则，不用AI排序。

建议稳定排序：
1. unmet prerequisite；
2. mastery升序；
3. recent error count降序；
4. last practiced更久优先；
5. business ID稳定tie-break。

规则必须版本化，例如：
`REC_RULE_V1`。

禁止通过开发过程中手调某几个学生case写身份特判。

## 7. WP-V04.5 — Learning Path

API：
- `GET /api/v1/knowledge-points/{targetId}/learning-path`

流程：
1. 获取course active graph version；
2. 获取target prerequisite subgraph；
3. 过滤 mastery >= 0.70 的节点；
4. 对剩余DAG做拓扑排序；
5. target最后（若未掌握）；
6. 每个节点返回当前 mastery状态、reason、可练ExerciseUnit。

必须处理：
- 无Published Graph；
- target不属于当前课程/无权限；
- target没有前置；
- 全部前置已掌握；
- 无可用Exercise；
- Neo4j不可用：明确失败/降级，不自行编路径。

V0.4不允许在Java里维护第二套 prerequisite 真相。

## 8. WP-V04.6 — Structured Explanation

推荐解释必须来自结构化事实：
- mastery score；
- attempt/correct counts；
- prerequisite关系；
- recent errors；
- graphVersion；

ReasonCode至少：
- `UNMET_PREREQUISITE`
- `LOW_MASTERY`
- `RECENT_ERRORS`
- `REVIEW_DUE`
- `TARGET_PRACTICE`

不得让LLM决定是否推荐。

学生端新增：

- 薄弱知识；
- 推荐练习列表；

## 10. Redis

Redis允许用于：
- mastery read cache；
- recommendation snapshot cache；

但MySQL始终是Mastery和Recommendation审计事实源。

缓存key必须带：
- studentId
- courseId
- algorithmVersion / graphVersion as applicable

缓存失败不能阻断Answer事实写入。

## 11. 测试

### Rule Mastery unit tests
至少：
- first correct = 2/3；
- first wrong = 1/3；
- repeated updates；
- multiple KnowledgePoint mappings；
- no mapping；
- same answer duplicate event exactly-once；
- inactive/cross-course rejection。

### Recommendation unit tests
至少：
- prerequisite优先；
- lower mastery优先；
- inactive过滤；
- no-question过滤；
- deterministic ties；
- explanation字段与排序原因一致。

### Learning Path
至少：
- chain A→B→C；
- branching DAG；
- mastered prerequisite removal；
- no graph；
- no prerequisite；
- no exercise；
- graphVersion mismatch。

### MySQL Testcontainers
- V004 migration；
- answer + mastery worker exactly-once；
- rollback/retry；
- history；
- recommendation snapshot persistence。

### Neo4j + MySQL integration
- 使用V0.3 Published Graph查询生成真实learning path；
- active graph version切换后推荐/路径绑定新版本；
- projection failure期间仍使用旧active version。

### Regression
V0.2 + V0.3全部现有测试必须继续通过。

## 12. 性能工程目标（不是生产实测声明）

在开发数据规模下：
- mastery GET P95目标 < 500ms；
- recommendation/path P95目标 < 1s；
- 单个mastery event处理不做全课程扫描。

实际测试结果与硬件必须在交付报告中记录。

## 14. Gate

只允许：
- `GO_V0.5`
- `CONDITIONAL_GO`
- `NO_GO`

GO最低要求：
1. Answer→Outbox→Mastery exactly-once闭环真实通过；
2. Rule mastery可解释且数据一致；
3. 推荐结果确定性、可审计；
4. 学习路径真实使用active Published Graph；
5. MySQL/Neo4j集成测试通过；
6. 全仓库CI通过；
7. 不依赖MODEL-0R即可工作。

完成后停止，等待架构审查；不得自动进入模型生产集成。
